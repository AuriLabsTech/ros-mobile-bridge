callService

  • callService(service, request, options?): Promise<Record<string, unknown>>

  • Call a ROS service and resolve with its response. options.timeoutMs bounds the individual call (see CallServiceOptions.timeoutMs for the per-transport mechanics); zero or below throws synchronously. Omitting it preserves the default behavior exactly.

    Resolves only with a response the client decoded. When the server answered but the client cannot read the answer (no schema for it, an encoding it does not decode, bytes that do not fit the schema, or a malformed payload), the promise rejects with ServiceResponseDecodeError, which carries the payload as bytes and the case as reason. That rejection means the call reached the server; it says nothing about whether the service succeeded. Rosbridge never produces it, because the bridge decodes the response itself.

    On Foxglove WebSocket the bridge lists its services just after connect() resolves. A call made before that list arrives, to a service not yet known, waits for it (at most 2 s, once per connection) and then goes ahead; a service still not listed then rejects as not available. That wait comes before timeoutMs starts counting.

disconnect

  • disconnect(): Promise<void>

  • Close the connection on purpose. No automatic reconnect follows.

    Before the socket closes, every pending priority: 'control' publish is sent, however many are queued. The library sends no stop of its own: to halt a robot on the way out, publish a zero geometry_msgs/msg/Twist to each velocity topic you drove, with priority: 'control', then call disconnect():

    const zero = { linear: { x: 0, y: 0, z: 0 }, angular: { x: 0, y: 0, z: 0 } };
    client.publish('/cmd_vel', 'geometry_msgs/msg/Twist', zero, { priority: 'control' });
    await client.disconnect();

    On rosbridge, every disconnect() of an open connection then waits for the bridge to work through what was written before closing, because the bridge drops messages it has received but not yet processed when the connection closes. It sends one /rosapi/get_time request last and closes on the answer, or after 2 s if none comes: usually one round trip, longer on a busy robot computer. That wait covers whatever was written last, at either priority, including a goal cancel or a service call sent just before. A connect() made during that wait connects once the close is done.

    Safety boundary. This only helps while the socket is open. Nothing can stop the robot on an unexpected loss of connectivity (network drop, app kill, crash): the transport is already gone, so no command can leave the device. Halting on network loss must be enforced robot-side, by a cmd_vel timeout or watchdog that stops the robot when commands stop arriving.

    Called while a connect() is in flight, it cancels that attempt.

    Returns Promise<void>

getParameters

  • getParameters(node, names, options?): Promise<ParameterReading[]>

  • Read parameters of node: one ParameterReading per name in names, in the same order.

    A ROS 2 node answers a request naming any undeclared parameter, or any declared one without a value, with nothing at all for the whole request. The library sends the names together and, when that happens, asks again one name at a time, so one bad name never hides the others. A name that still comes back empty is described once to tell 'not-set' from 'undeclared'. A node started with allow_undeclared_parameters answers for every name as if it were declared without a value, so on such a node an unknown name reads as 'not-set', never 'undeclared'.

    On rosbridge the bridge never sends a reply that holds a non-empty byte array, so the library first asks the parameters' types and does not read the byte-array ones: each comes back as 'unreadable' (an empty one too, since its length is not known without reading it), and the rest are read as usual.

    options.timeoutMs bounds each request, not the whole call: a read that has to re-ask names one at a time, or describe them, makes several requests in turn, so the call can take a few times timeoutMs.

getPublishPermission

  • getPublishPermission(): PublishPermission

  • Whether the server accepts publishing from this client, as far as the transport says: 'allowed', 'refused', or 'unknown' (ADR 0022). Use it to grey out command controls before the user touches them.

    • Foxglove WebSocket: 'allowed' when the bridge's serverInfo lists the clientPublish capability, 'refused' when it does not. A foxglove_bridge launched without clientPublish in its capabilities parameter drops everything you publish, while publish() still returns normally and the status stays 'connected'.
    • rosbridge: always 'unknown'. The protocol has no server-wide signal for it, and a topic refused by the server's topics_pub_glob is dropped with nothing on the wire.
    • Before the first handshake and after disconnect: 'unknown'.

    The answer is server-wide. 'allowed' does not promise a given topic gets through: a per-topic rule on the server (rosbridge topics_pub_glob, a Foxglove topic whitelist) can still drop it. publish() behaves the same whatever this returns; the library does not drop or throw on 'refused'.

    The value changes only at a handshake, so re-read it when IProtocolClient.onStatusChange reports 'connected'; it is already current inside that callback.

    Returns PublishPermission

getSubscriptionState

  • getSubscriptionState(topic): SubscriptionState

  • Establishment state of the subscription on topic: 'none' | 'pending' | 'active'.

    subscribe() on a topic the bridge has not advertised yet succeeds and returns a working unsubscribe function, but the subscription cannot be established at the bridge until the topic appears; until then it is 'pending' and no messages can arrive. The client cannot tell a typo'd topic from one that will appear later (a robot mode switch that starts new publishers, a node still launching) — only the app can judge that, so the state is surfaced instead of timed out.

    'active' means established, not delivering:

    • A quiet topic (no publisher, or nothing published yet) is 'active'. Topic liveness is a separate question — getAvailableTopics() / onTopicsChange.
    • A subscription paused by its circuit breaker stays 'active'; breaker state has its own observer, getBreakerState.
    • On rosbridge, a subscription typed via SubscribeOptions.schemaName reports 'active' immediately. If the supplied type turns out wrong, 'active' can overstate until topic discovery reports the real type and the client re-subscribes with it (see SubscribeOptions.schemaName).

    Getter only, by design: every pending → active transition coincides with an event the consumer can already observe (the topic appearing fires onTopicsChange; delivery fires the message callback itself). A "waiting for topic" badge is a small wrapper:

    const unsub = client.subscribe('/mode_gated/status', onMsg);
    const render = () =>
      setBadge(client.getSubscriptionState('/mode_gated/status') === 'pending');
    render();
    const stop = client.onTopicsChange(render);

getTopicEndpoints

  • getTopicEndpoints(topics?): Promise<TopicEndpoints[]>

  • Which nodes publish and which subscribe to each topic, as a snapshot taken now. Use it to tell a robot's command inputs (nodes subscribe) from its sensor outputs (nodes publish).

    Needs ProtocolClientOptions.readTopicEndpoints. With that option off, every side of every topic is null (not known), on every transport.

    With topics, the answer has one entry per distinct name, in the order given, and the client asks only about those topics. Without it, the answer covers every topic the transport knows, sorted by name. A side is null whenever the client cannot vouch for it; see TopicEndpoints.

    The answer never lists the bridge this client talks through. The bridge shows up in the robot's graph as an endpoint of every topic its clients touch, this app's included, under one node name for all of them, so its entries describe apps rather than the robot. The client leaves it out only on evidence of its name, and when it has none the affected sides are not known. On Foxglove WebSocket a second bridge on the same robot is listed like any other node. On rosbridge, every node that publishes a client_count topic is taken for a bridge and left out, since the client cannot tell its own bridge from another one that way. Nodes started from the command line (ros2 topic pub) are listed where the transport reports them: Foxglove WebSocket does, rosbridge does not.

    Nothing is updated live, and there is no change callback: call it again when you want a fresher answer. One lookup runs at a time; a call made during a lookup for the same topics shares its answer, and any other call waits for it to finish. Rejects with "Not connected" when called while disconnected, and when the connection ends or changes mid-lookup.

    Transport notes:

    • Foxglove WebSocket reads the bridge's own map of the robot's graph. That map is only right once the bridge has rebuilt it while this client was listening, and the bridge rebuilds only when the graph changes. Until then every side is not known. In practice this app's first topic subscription triggers a rebuild. A change made in the last second or so may not be in the answer yet. The bridge's name is learned from the topics this client has subscribed to or advertised for at least two seconds; before that, or when another node is on every one of those topics too, every side is not known.
    • rosbridge asks the bridge's rosapi node, one question at a time, with a timeout on each, and stops at the first failed question; every side not yet answered is then not known. Read the risk under ProtocolClientOptions.readTopicEndpoints before turning it on. The bridge's name is the publisher of its client_count topic. rosapi sees the graph through its own node, which can lag the robot by a moment, most likely just after the robot starts: an empty side then may be stale, and asking again a couple of seconds later gets the fresh answer.

onStatusChange

  • onStatusChange(cb): (() => void)

  • Call cb with each new ConnectionStatus. cb is also called once, right away, with the current status. Returns a function that removes cb.

    After that first call, a status is reported only when it changes. Subscriptions do not survive a reconnect: resubscribe when the status changes to 'connected'. The first call can itself be 'connected' when you register on a client that is already connected, so a handler that resubscribes should skip it (or track the previous status), or it subscribes twice.

    By the time cb hears 'connected', the connect() call that led there has already succeeded. Calling disconnect() from inside cb closes the connection; it does not turn that connect() into a cancellation.

sendActionGoal

  • sendActionGoal(action, _actionType, goal, options?): ActionGoalHandle

  • Dispatch a ROS 2 action goal and return a minimal handle for it, synchronously. Throws when the client is not connected.

    handle.outcome resolves on any terminal state — SUCCEEDED (4), CANCELED (5), ABORTED (6) — with the action_msgs/msg/GoalStatus value and the result payload; a canceled or aborted goal is a resolution, not an error, because the lifecycle was observed to its end. It also resolves {status: 0} (STATUS_UNKNOWN) when the server answers that it no longer knows the goal — its specified disowning answer, typically after result_timeout eviction — entered on that positive evidence only, never inferred from silence; see ActionGoalOutcome.status. A goal that produces no evidence at all stays pending forever. It rejects with ActionGoalError only when there is no lifecycle to report; branch on its reason with a default case. The 'disconnected' reason means the outcome became permanently unobservable while the robot may still be executing — reassess robot state on reconnect rather than treating it as goal failure.

    options.onFeedback registers a best-effort per-goal progress callback (newest state wins under pressure, no rate guarantee); consumers who need every frame subscribe to the action's feedback topic themselves. The handle never times out on its own — patience is the caller's decision (Promise.race), and cancel() is the giving-up mechanism, safe on a goal that never started.

    Two situations leave a goal pending with no further evidence coming: an action that is still advertised whose server has died, and a goal the server declined whose reply was lost on the way back. Neither is distinguishable from a goal that is simply taking a long time, so an application that needs a deadline sets its own:

    const handle = client.sendActionGoal('/dock', 'my_robot/action/Dock', goal);
    const deadline = new Promise<never>((_, reject) =>
      setTimeout(() => reject(new Error('dock did not finish in 60s')), 60_000),
    );
    try {
      const outcome = await Promise.race([handle.outcome, deadline]);
    } catch (err) {
      handle.cancel();
      throw err;
    }

    handle.acceptance resolves with the server's decision to execute the goal ('accepted', 'rejected' or 'unobservable') from whatever evidence the transport provides, and never rejects. It is prompt on Foxglove WebSocket, where the dispatch response carries the flag, and late on rosbridge, where the bridge does not relay it and the first feedback frame or the terminal is the evidence. Cancel-by-UUID, cancel-all, and action discovery remain reachable via callService on the action's services where the transport exposes them.

    If you do call <action>/_action/send_goal yourself, put the goal's own fields at the root of the request beside goal_id, not under a goal key. rosidl inlines them: three nav2 send-goal schemas captured from a live bridge (jazzy, foxglove-sdk-cpp v0.25.1) all declare the flat shape and none declares a nested one. Getting this wrong is silent rather than fatal, which is what makes it worth stating: CDR carries no field names, so a nested payload encodes without error, every real field is written from its schema default, and the robot executes a goal nobody sent. sendActionGoal encodes from the advertised schema and is correct either way; a hand-built request is not.

    // Correct: the goal's fields ride at the root.
    await client.callService('/dock/_action/send_goal', {
      goal_id: { uuid: myUuidBytes },
      use_dock_id: true,
      dock_id: 'bay-3',
    });

    Transport notes: on rosbridge the client speaks the native send_action_goal op family; the bridge's internal action client holds a standing result request from acceptance, so the status-0 disowning case never arises there — one contract, and rosbridge simply never produces the middle value. On Foxglove WebSocket the client composes dispatch from the hidden _action/* services and topics, which exist only when the bridge runs with include_hidden:=true; on a stock Foxglove bridge the outcome rejects fast with reason 'unavailable'. A goal sent before the bridge's first service list has arrived waits for that list (at most 2 s, once per connection, as callService does) and is then sent; a cancel() made during the wait is sent after the goal. The terminal result rides a standing get_result request armed when the status topic first names the goal — immune to result eviction on every distro and free of any client-side ceiling on goal duration. That same watch is what lets the Foxglove client carry a goal whose send_goal reply went missing at the bridge: the goal id is invented here before the request is sent, so a status entry naming it proves the server holds the goal, and from that point the server outranks any bridge-level failure. Over rosbridge that recovery is not available, because the bridge relays the goal without the client's goal id and never surfaces the one it mints, so no status entry there can be matched to this goal.

    Note for consumers that implement IProtocolClient themselves (test doubles, most commonly): the interface is the contract between the library and its transports; additions to it ship in 0.1.x releases. Prefer extending a shipped client or implementing a partial view.

subscribe

  • subscribe(topic, onMessage, options?): (() => void)

  • Subscribe to a topic. Returns an unsubscribe function.

    If options.maxFrequency is set, the client drops messages without parsing them when they arrive sooner than 1000 / maxFrequency ms after the previous delivery to this callback. Throttle state is per-callback, so multiple subscribers to the same topic with different rates are isolated.

    Synchronous callback contract. onMessage is invoked synchronously on the message-handler tick after the per-tick throttle / breaker decisions have already run. A callback that performs heavy work synchronously (an expensive decode, a synchronous render pipeline) blocks the JS thread for the callback's duration — including blocking the lag probe that informs the library's own adaptive throttle and circuit breaker. Under sustained overload this lets queued messages bypass throttle decisions that would otherwise drop them, because the decisions are made at message-arrival granularity, not at callback-completion granularity.

    The library cannot bound consumer callback duration without breaking the synchronous contract that ordering-sensitive consumers depend on. Yielding via setImmediate, queueMicrotask, or requestIdleCallback is the consumer's responsibility. The canonical shape for heavy work is defer + skip-if-still-processing + latest-wins:

    let pending: RosMessage | null = null;
    let processing = false;
    client.subscribe('/camera/raw', (msg) => {
      pending = msg;                   // latest-wins; older value discarded
      if (processing) return;          // a deferred decode is in flight
      processing = true;
      setImmediate(() => {
        while (pending) {
          const next = pending;
          pending = null;
          decodeAndRender(next);
        }
        processing = false;
      });
    });

    SubscribeOptions.dispatchMode: 'latest-only' ships the latest-wins half of this pattern as a built-in, and conflates upstream of the parse — see its documentation.
