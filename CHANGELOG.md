# Changelog

All notable changes to `ros-mobile-bridge` will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **`sendActionGoal()` dispatches a ROS 2 action goal from every client, closing the largest capability gap between the two transports.** `IProtocolClient` gains `sendActionGoal(action, actionType, goal, options?)`, returning a goal handle synchronously: `outcome`, a promise for the terminal state, and `cancel()`. The `outcome` promise resolves when the goal reaches any terminal state, carrying the `action_msgs/msg/GoalStatus` value (4 SUCCEEDED, 5 CANCELED, 6 ABORTED) and the result payload; a canceled or aborted goal is a resolution, not an error, because the lifecycle was observed to its end. A third resolution, `{status: 0}` (the wire's own STATUS_UNKNOWN), reports the server disowning the goal: ROS 2 action servers discard a result `result_timeout` seconds after it is produced (10 s by default on current C++ servers), and a `get_result` for a discarded or never-known goal is answered immediately with status 0 and a zero-filled result payload that carries no information. The library resolves status 0 only on that positive evidence, the server's own answer, never from silence or a timer; it means no reachable server knows the goal any longer, which is deliberately weaker than CANCELED or ABORTED (nothing is known about how execution ended) and stronger than pending (the goal is not executing on any server the client can see), and after it `cancel()` has nothing to reach. A goal that produces no evidence at all, such as a server dying mid-goal and never returning, stays pending under the no-deadline rule below. It rejects only when there is no lifecycle to report, with the new exported `ActionGoalError` whose `reason` field distinguishes `'rejected'` (the server declined the goal), `'unavailable'` (no action server), `'disconnected'` (the connection closed mid-goal, after which the outcome is permanently unobservable while the robot may still be executing), and `'server-error'`, with the server's verbatim message in `detail`. The `reason` union may gain members in future releases; branch with a default case. `options.onFeedback` registers a per-goal progress callback at dispatch time, the shape native ROS 2 clients use; its contract is best-effort progress where the newest state wins under pressure, with no rate guarantee, and consumers who need every frame subscribe to the action's feedback topic themselves. The handle carries no deadline and never times out on its own: the library cannot distinguish a slow goal from a dead one, so patience is the caller's decision (`Promise.race` against a timer), and `cancel()` is the giving-up mechanism, safe to call even if the goal never started. Goal acceptance is deliberately not part of the contract on either transport, since the rosbridge wire cannot observe it; callers who want the acceptance signal on Foxglove keep using `callService` on the action's services directly, which remains fully supported, as do cancel-by-UUID, cancel-all, and action discovery. Transport notes: on rosbridge the client speaks the native `send_action_goal` op family. On any normally launched bridge, goals run in their own thread and do not delay other traffic, because both the standard executable and the launch file override the `send_action_goals_in_new_thread` parameter to true; a deployment that explicitly sets it false serializes every subsequent op behind a running goal until it ends (rosbridge_suite issue #909), with goal cancellation as the one op that jumps that queue. On Foxglove WebSocket the client composes dispatch from the hidden `_action/*` services and topics, which exist only when the bridge is launched with `include_hidden:=true`; on a stock Foxglove bridge `sendActionGoal` fails fast with `'unavailable'`. The terminal result travels on a standing `get_result` request, armed when the action's status topic first names the goal and answered by the server at the terminal transition, so the outcome is immune to result eviction on every distro (including Humble, where the eviction clock runs from acceptance rather than from the terminal state) and a goal of any duration is observable, with no service-timer ceiling on the terminal channel; if the goal later disappears from the status topic, the client probes `get_result` once and resolves status 0 only on the server's own STATUS_UNKNOWN answer. On rosbridge the disowning case cannot arise at all: the bridge's internal action client holds the equivalent standing result request from acceptance, so the contract is one and the same on both transports and rosbridge simply never produces the status-0 middle case; its real orphan, an action server dying mid-goal, produces no frame ever and is covered by the pending-forever rule. Note for consumers that implement `IProtocolClient` themselves (test doubles, most commonly): the interface is the contract between the library and its transports, and additions to it ship in 0.1.x releases; prefer extending a shipped client or implementing a partial view.

- **`callService()` accepts a per-call timeout.** The optional third parameter `{ timeoutMs }` bounds an individual call. On rosbridge it is forwarded as the protocol's `timeout` field, so the bridge itself gives up and returns a failure frame carrying its reason (for example "Timeout exceeded while waiting for service response") instead of the caller guessing from silence; a local backstop is armed slightly later than the wire deadline, so the server's reasoned answer always wins when one is coming and the backstop fires only when no frame will ever arrive, as under a restrictive `services_glob`. On Foxglove WebSocket, which has no wire-level equivalent, the value governs the local timer directly. Values of zero or below throw synchronously: on the rosbridge side `timeout: 0` means an unbounded server-side wait whose worker outlives the client's disconnect, so it is never forwarded. Omitting the option preserves existing behavior exactly, including the wire frames sent.

### Fixed

- **An E-Stop that publishes to more than three distinct control topics now reaches all of them, instead of silently dropping the overflow.** `disconnect()` drains pending control-priority publishes before closing the socket, and that drain is what carries a release-the-joystick zero Twist, or an action cancel, to the robot on the way out. It shared the live path's per-tick limit of three entries: it sent three, re-armed itself for the rest with `setTimeout(0)`, and then `disconnect()` closed the socket. When the re-armed flush finally ran it found the socket shut and cleared the remaining entries unsent, reporting nothing, on both transports. How many entries are pending is governed by conflation rather than by publish rate: the outbox conflates per destination, so the count is the number of distinct control topics with a publish in flight, not a burst on one topic. An app driving a single robot from one teleop widget never had more than one or two entries and was never exposed, which is why this went unseen; an app with several teleop widgets or several robots, each publishing to its own `cmd_vel`, exceeded three routinely and lost the tail of its own stop command. The teardown drain is now uncapped, bounded by that same per-destination conflation instead of by a counter. The live path is deliberately unchanged: it still sends at most three per tick and re-arms for the remainder, which is what keeps a saturated JS thread from spending an unbounded slice in the outbox. Only teardown, where there is no next tick to re-arm into, ignores the limit. No public API change.

- **A Foxglove WebSocket subscription now survives its channel being unadvertised and re-advertised, including under a new channel id.** An action-server restart makes `foxglove_bridge` drop the action's hidden channels and re-advertise them under new ids (measured on a live bridge: status and feedback returning as different channel numbers), and the same sequence arises for any topic whose publisher node restarts while no other client holds it in the graph. Previously the client noticed the unadvertise and forgot the channel, but the subscription stayed bound to the dead id: alive in every observer, permanently silent on the wire, with a reconnect as the only repair. Now the subscription is demoted to pending when its channel goes away — `getSubscriptionState` reports `'pending'`, honestly, while the topic is gone — and the ordinary pending-activation path re-subscribes it the moment the topic reappears, whatever id it comes back under. Callbacks, rate caps, and dispatch modes carry over. Two existing contracts are preserved through the churn: a `latest-only` trailing frame stashed before the unadvertise is still delivered when its window reopens, labelled with the channel that carried it (the v0.1.9 contract), and unsubscribing inside the churn window still drops the stashed frame rather than delivering after unsubscribe. Unsubscribe functions obtained before the churn remain valid throughout. No public API change.

## [0.1.9] - 2026-08-03

### Fixed

- **A rate-capped `latest-only` subscription now delivers the last message before a topic falls silent, instead of discarding it.** The per-callback rate cap was a leading-edge gate: it admitted the first message in each window and discarded the rest, with no trailing delivery. On a topic that keeps publishing that is harmless, because a discarded message is restated by the next one a bounded time later. On a topic that publishes on change and then goes quiet, the loss is permanent, and it is silent: nothing arrives afterwards to contradict the stale value the callback is left holding. Action goal status is the clearest casualty, since a goal reaching a terminal state is exactly the moment its status topic stops publishing, so a goal that had finished could be left rendered as still running indefinitely, but the defect was never specific to actions. Any capped subscription to a topic that falls silent was exposed, an e-stop assertion and a map update among them. A second half of the same defect made it far easier to hit than it looks: `latest-only` was inert whenever a cap was in force, because the eligibility test ran upstream of the conflation stash, so no message could ever supersede the one waiting and the number of survivors per window was one by construction. The message delivered from a burst was therefore the oldest, not the newest, which is the opposite of what the mode promises. And a cap is essentially always in force, because the adaptive throttle boots every new subscription at a non-zero floor before any lag is measured, so this was the default state at subscribe time rather than a loaded-system edge case. Four changes fix both halves. The stash is now unconditional, so a message arriving inside a closed window supersedes the pending one instead of being dropped. The deferred drain is armed for the moment the window reopens rather than for the next tick. The delivery clock advances at delivery rather than when a message is stashed, so the cadence is paced by deliveries and a capped subscription fed faster than its cap now delivers at exactly its cap. And the drain re-checks the window before firing, re-arming for the remainder if the adaptive throttle widened the interval in the meantime, so a widening cap defers a message rather than releasing it early. The net contract: a rate cap now shapes when the newest message is delivered, never whether it is, and the last message before silence always arrives, at most one window late. Consumers will see additional deliveries on capped `latest-only` subscriptions that previously never arrived, each carrying the newest message as of the moment its window reopened; an app that worked around this by disabling the cap on a topic it could not afford to lose can restore the cap. `immediate` is deliberately unchanged and remains leading-edge, since its contract is synchronous delivery on the message-handler tick and a trailing message can only be delivered off it. Conflation restores the final state, so it does not repair a topic where every message is a distinct record that no later message restates; the honest answer there remains not to cap it. No public API change.

- **A deferred `latest-only` message is now labelled with the channel it arrived on, rather than with whatever the client knows at the moment it is delivered.** The encoding and schema name were read when the deferred drain ran, not when the message was stashed, so anything that changed the client's view of the topic in between corrupted the delivered message. On Foxglove the trigger is a channel closed while a subscription is live: the server sends `unadvertise`, the client drops the channel, and the trailing message, which is exactly the one this release exists to deliver, came out labelled `encoding: 'json'` with an empty `schemaName`, after which the JSON path failed to parse CDR bytes and handed back the raw payload instead of the decoded object. Nothing forbids that sequence. The protocol's `unadvertise` definition says nothing about subscriber state, and the Foxglove SDK's own WebSocket server unadvertises a closed channel regardless of who is subscribed, a behavior its test suite pins deliberately. One server deserves a specific note because it is the common one: `foxglove_bridge` derives its channel set from the ROS graph, and the ROS subscription it creates on behalf of a WebSocket subscriber keeps the topic present in `rmw_get_topic_names_and_types`, documented normatively as listing topics for which a publisher and/or a subscription exists. A publisher dying therefore does not remove the channel there while any client is watching it, so on that bridge this sequence does not arise from publisher death; it arises on any server that closes a channel directly. On rosbridge the path is ordinary rather than exotic: topic discovery re-typing a topic while a drain is armed, which the 0.1.7 self-heal does by design, since it revises a subscription's recorded type in place and leaves armed drains untouched. Encoding and schema name are now captured at stash time and travel with the payload, so a message is always described by the channel that actually carried it. That is the protocol's own reading rather than a defensive choice: a message payload is defined as encoded per the Advertise corresponding to its channel, making the encoding a property of the advertisement that introduced the frame and not of whatever the channel map happens to hold when the frame is finally parsed. Previously the corrupting event had to land inside a single `setTimeout(0)` gap and was close to unreachable; trailing delivery widens that window to the full throttle interval, up to two seconds under the adaptive floor, which is what turned it into a real defect and why it is fixed here rather than separately.

### Documented

- **`maxFrequency: 0` is now documented as the explicit spelling of "no user cap", exactly equivalent to omitting the field.** Both forms were already supported and are now covered by tests on both clients, so the behavior is pinned rather than incidental: `0` is the natural choice when the value arrives from a variable or a settings store. The TSDoc also states the half that is easy to get wrong, that `0` waives only this cap while the adaptive throttle still applies its own floor, so `{ maxFrequency: 0, disableAdaptive: true }` is the supported way to say "deliver every message, gate nothing". The documented scope is `0`; negative and `NaN` reach the same internal branch as an implementation detail and are not part of the contract.

## [0.1.8] - 2026-07-31

### Fixed

- **Foxglove service calls now read the schema a modern bridge actually advertises, so services outside the built-in bundle work again.** An `advertiseServices` entry can carry its schema in two shapes: the nested `request` / `response` objects, which is the current form, and the flat `requestSchema` / `responseSchema` pair, which the ws-protocol spec keeps only "for backwards compatibilty, prefer using `request` instead". The client read only the flat pair, and a stock `foxglove_bridge` 3.4.1 (foxglove-sdk-cpp v0.25.1) sends the nested objects on every service and the flat fields on none of them. The schema was on the wire the whole time and was never read. Two consequences followed, one loud and one silent. A non-empty request against any type outside the six-entry fallback bundle failed to encode, reporting that the bridge had advertised no schema, which was wrong: `callService('<action>/_action/send_goal', goal)` could not dispatch an action goal at all, and neither could any ordinary service carrying fields. A response for such a service resolved to `{ rawBytes }` with no error at all, so a call that appeared to succeed handed the consumer undecoded bytes instead of the response object. Both were masked for exactly the types the bundle covers, which is why `_action/cancel_goal` kept working while `_action/send_goal` did not. The nested objects are now read first on both the request and response sides, with the flat pair kept as the documented fallback for older bridges; the two forms are never mixed, so a schema is never parsed under an encoding hint belonging to a different string. An advertised schema that cannot be parsed is no longer fatal either: it logs a warning naming the service and the parse failure, then falls through to the bundle, which is the behavior the bundle was always described as providing. The request and response paths now share one implementation, since only the request side fails loudly and the drift between them is what let the silent half go unnoticed. The error text for a genuinely unusable schema no longer blames the bridge for omitting one. No public API change.
- **A default payload derived from a schema now fills fixed-length arrays instead of leaving them empty, so `{}` works as a default request for any type containing one.** Both `getSchemaTemplate` and the Foxglove service-call encoder derive a default payload by zero-filling a parsed message definition, and every array field was filled with `[]` regardless of whether the definition declared a fixed length. A fixed-size array (`uint8[16]`) carries no length prefix in CDR, so the writer requires exactly that many elements and rejected the template with `Expected 16 items for fixed-length array field uuid but received 0`. The visible casualty was action cancellation over Foxglove WebSocket: `action_msgs/srv/CancelGoal` nests `unique_identifier_msgs/UUID`, so `callService('<action>/_action/cancel_goal', {})` threw at encode time instead of producing the all-zero goal id and zero stamp that `CancelGoal` documents as "cancel every goal on this action", which is the form an unconditional stop path depends on. Fixed-length arrays now materialize `arrayLength` zero-valued elements. Variable-length (`T[]`) and bounded (`T[<=N]`) arrays are legal when empty and are unchanged, as is any request that supplied the field explicitly. The same defect was present on the JSON Schema path, which a bridge advertising `jsonschema` rather than `ros2idl` takes: `jsonSchemaToTemplate` returned `[]` for every array and never read `minItems`, so a template derived from such a bridge was invalid against its own schema for any type carrying a fixed-size array, `sensor_msgs/Imu.orientation_covariance` (`double[9]`) among them. A ROS fixed-size array reaches JSON Schema as `minItems === maxItems === N`, and that many zero-valued elements are now produced, built from the `items` schema so complex element types are filled too. Arrays with no `minItems`, with `minItems: 0`, or with only a `maxItems` bound stay `[]`, and an explicit `default` still wins over the derived value. Both halves of the fix are behavior-only: no public API change.

## [0.1.7] - 2026-07-27

### Added

- **`subscribe()` on a topic the bridge has not advertised yet now creates a pending subscription on every client instead of failing silently.** The subscription activates automatically when the topic appears, and the returned unsubscribe function cancels it at any stage. New `getSubscriptionState(topic)` reports `'none' | 'pending' | 'active'` so an app can render a "waiting for topic" state; breaker state remains a separate observer, and `'active'` means established at the bridge, not delivering. New optional `SubscribeOptions.schemaName` supplies the message type up front: on rosbridge this establishes the subscription immediately, even before a publisher exists; on Foxglove it is ignored. If the supplied type disagrees with what topic discovery reports, the client re-subscribes with the discovered type. One caveat on rosbridge: a hinted subscription to a topic that does not exist yet is itself an endpoint in the ROS graph, and discovery reports a single type per topic (the alphabetically first among its endpoints' types), so a wrong hint that sorts before the true type is echoed back as the topic's own type, the correction never fires, and the subscription stays established but never delivers. Hint only types known from the robot's interface contract; a wrong hint on a topic with a live publisher at subscribe time is always corrected. Pending subscriptions follow the existing reconnect contract, cleared on disconnect, resubscribed by the consumer. `subscribe()` while not connected remains a no-op and now behaves identically on both clients (both warn and return a no-op closure). No changes required to existing code.
- **`connect()` accepts an `AbortSignal` to cancel an in-flight connection attempt.** Every client's `connect(url)` gains an optional second parameter, `ConnectOptions` (`{ signal?: AbortSignal }`), and `ProtocolManager.connect(options)` forwards the same bag as its own second parameter. Aborting the signal before the handshake completes closes the socket and rejects the pending `connect()` promise with `signal.reason` when the runtime provides one, or an `Error` whose `name` is `'AbortError'`; branch on `err.name === 'AbortError'`, as with `fetch`, never on `instanceof`. Cancellation is not a failure: status lands on `'disconnected'` (not `'error'`), `getLastError()` is untouched, and no reconnect is scheduled. Aborting after `connect()` has resolved is a no-op; the signal governs the attempt, never the established connection, and `disconnect()` remains the way to end a live session. A pre-aborted signal rejects immediately with no socket created, and `ProtocolManager.connect` checks the signal before any side effect, so a pre-aborted call cannot tear down the currently active connection. No changes required to existing code.

### Changed

- **`npm pack` now rebuilds `dist/` via a `prepack` hook, so a tarball can never carry stale output.** Previously the build ran only on `npm publish` (through `prepublishOnly`), so a tarball packed without a preceding manual build shipped whatever `dist/` was on disk; two 0.1.6 release candidates were cut with stale output this way. The build step moved from `prepublishOnly` to `prepack`, which npm runs on pack, on publish, and when installing from a git reference; the lint, typecheck, and test guards stay on `prepublishOnly`. Consumers of the published package are unaffected.

### Fixed

- **rosbridge now re-subscribes a topic once its message type becomes known, instead of leaving the subscription permanently dead.** `subscribe()` resolves a topic's type once, from the discovered-topic set as it stands at the moment of the call. A topic whose publisher has not started yet is absent from that set, so its subscribe frame went out with no `type`, and a stock `rosbridge_server`, unable to infer the type of a topic nothing advertises, logged a rosout ERROR and never established the subscription. Nothing revisited it afterwards: the callback stayed silent for the life of the connection, and a consumer could not repair it either, since a second `subscribe()` for the same topic only appends a callback to the existing, dead entry. Only a reconnect recovered it. Now, when a discovery pass learns the type of a topic that has a subscription with no type, the client adopts the type and re-issues the subscribe, so a topic published by a late-starting node begins delivering within one discovery interval, with no reconnect. The repair runs at most once per divergence, never re-sends for a subscription whose recorded type matches what discovery reports (the comparison tolerates the 2-part ROS 1 spelling), and leaves a circuit-breaker-paused subscription off the wire while still recording the type that its half-open retry will use. When a recorded type disagrees with the discovered one (a wrong `SubscribeOptions.schemaName`, or a topic whose type genuinely changed), the corrective subscribe is preceded by an `unsubscribe`: a stock `rosbridge_server` silently rejects any subscribe whose type conflicts with the topic's established type, so a bare corrective frame would bounce off the stale registration. `onTopicsChange` still fires only on a real change to the topic set. No public API change from this fix on its own. This is a rosbridge-only change; the Foxglove client is not modified.
- **`disconnect()` during an in-flight connection attempt now settles the pending `connect()` promise.** Previously the attempt's socket handlers were detached before the socket closed, so the caller's `connect()` promise could never settle and hung forever. It now rejects with the same `'AbortError'`-named shape as a signal abort. The rejection is pre-handled by the library, so a caller that did not retain the promise (fire-and-forget `connect()` driving UI off status listeners) sees no unhandled rejection, while a caller awaiting it observes the rejection normally. Genuine connection failures are not pre-handled and keep their visibility.
- **Tearing down a mid-handshake connection no longer crashes a Node host that uses the `ws` package.** Connection teardown detached the socket's error handler before closing it. The `ws` package emits an `'error'` event ("WebSocket was closed before the connection was established") when a socket is closed while still connecting, and a `ws` socket is a Node `EventEmitter`, where an `'error'` event with no listener attached is thrown as an uncaught exception and brings down the process. Any teardown that lands before the handshake completes triggered it: a connection timeout against an unreachable robot, `disconnect()` during an attempt, or aborting via `AbortSignal`. Both clients now keep a no-op error listener on the socket through teardown. Browsers, React Native, and Node's built-in WebSocket are unaffected either way (their sockets tolerate unlistened error events); the crash was specific to Node consumers that supply the `ws` polyfill. No public API change.

## [0.1.6] - 2026-07-08

### Fixed

- **rosbridge now receives messages from a stock ROS 2 `rosbridge_server`.** A default `rosbridge_server` serializes outbound frames with ujson, which escapes `/` as `\/`, so topics arrive on the wire as `"\/model\/pose"`. The receive fast-path compared the raw, still-escaped topic against the subscription map, missed, and dropped every inbound `publish` before parsing it: no messages arrived at all, on both `immediate` and `latest-only` subscriptions, while outbound publishing still worked. The fast-path now unescapes the topic before matching, so it resolves the real subscription exactly as it does against a server that emits unescaped slashes. As a defensive follow-on, a topic that still does not match is deferred to the authoritative parse rather than dropped, so the pre-parse fast-path can only ever drop on a certain positive match. No public API change; Foxglove is unaffected (it routes messages by numeric channel id, not a topic string).
- **rosbridge no longer sends an invalid empty `type` on a subscribe with an unknown message type.** When `subscribe()` ran for a topic whose type was not known at that moment (subscribed before topic discovery populated the type list, or a topic absent from the discovered set), the client sent `type:""`. A stock `rosbridge_server` runs `get_message_class("")`, raises `InvalidTypeStringException`, logs a rosout ERROR, and never establishes the subscription, with no error op sent back to the client. The client now omits the `type` field when the message type is unknown, so a topic whose type rosbridge can resolve (for example from a live publisher) is subscribed instead of rejected. A topic with no resolvable type on the server (no publisher, unknown to the graph) still cannot be subscribed, since the type cannot be supplied by the client, but no malformed frame is sent for it. A known type is still sent verbatim, and the same path covers the circuit-breaker half-open re-subscribe. No public API change; Foxglove subscribes by numeric channel id and is unaffected.

## [0.1.5] - 2026-07-08

### Added

- **`ProtocolMismatchError`: a typed error raised when a client is pointed at a server speaking the other protocol.** It carries `expectedProtocol` (the client's own transport) and `detectedProtocol` (`'foxglove-ws'` / `'rosbridge'` / `'zenoh'`, or `'unknown'` when only the negative is known), and ships a clear, ready-to-show `message`. It is surfaced on both transports. The Foxglove client rejects `connect()` with it when the WebSocket opens but no `serverInfo` handshake arrives. The rosbridge client, which resolves `connect()` at socket open, detects a Foxglove-only frame (`serverInfo`, or an `advertise` carrying a `channels` array) after connect, transitions status to `error`, and exposes the error through the new `getLastError()`. Detection on the rosbridge side is precise: a real rosbridge server never sends those frames.
- **`IProtocolClient.getLastError(): Error | null`** returns the most recent error that drove the connection into a failure, or `null`. Read it on a `status === 'error'` transition to recover the reason; it is the only channel for a protocol mismatch detected after `connect()` has already resolved. Cleared at the start of the next `connect()`.
- **`getSustainedLagMs(): number` is now a public diagnostics export.** It returns the sustained JS-thread lag (the 75th percentile of probe samples over the last 4 s), the *relax* input to the adaptive throttle, alongside the already-exported `getMaxLagMs()` (1 s max, the *tighten* input). Both are `() => number` readers over the shared event-loop monitor. Exposing it makes the throttle's two controller inputs symmetric on the public surface: a consumer recording why the cap moved can now log the relax signal, not only the tighten signal. No behavior change; the value was already computed and used internally.

### Changed

- **Adaptive throttle controller dynamics reworked so the cap settles instead of hunting and recovers instead of ratcheting down.** Tighten and relax now read different signals across a deadband. Tighten reacts immediately to the worst-case lag spike (the 1 s rolling max), as before. Relax steps back only when a sustained lag percentile (a new several-second reading) falls a deadband below the bucket's threshold, then jumps straight to the justified bucket rather than one step per dwell. Three consequences: jitter around a threshold no longer makes the cap oscillate (it holds inside the deadband); an isolated main-thread spike no longer resets recovery, so a stream of isolated GC or animation spikes can no longer ratchet the cap one-way; and time from the floor back to uncapped is bounded to about one relax window instead of one bucket per dwell. No public API change: the preset shape and values, the cap label, and the throttle observers (`getSubscriptionStats`) are unchanged. The lag signal remains global (one JS thread), which is intentional and load-bearing.

### Fixed

- **rosbridge now re-discovers topics on every reconnect and mid-session, matching Foxglove's push-driven freshness.** Previously the discovered-topic list was fetched once and never refreshed, so after an automatic reconnect to a host now serving a different robot (or after a topic was advertised mid-session) `getAvailableTopics()` and `onTopicsChange()` kept reporting the previous set. Re-discovery now runs on every (re)connect, with a bounded retry for the empty-first-result race (a host that has not re-attached the robot yet), and reuses the latency probe's existing `/rosapi/topics` call for mid-session changes rather than adding a second timer. `onTopicsChange()` fires only when the topic set actually changes. No public API change; Foxglove is unaffected.
- **A re-advertised topic stays subscribable on Foxglove WS.** Unadvertising a stale channel id no longer deletes the topic-to-channel mapping when the same topic was already re-advertised under a new id; the mapping is cleared only when it still points at the unadvertised id.
- **A bracketed IPv6 host with a port no longer builds an invalid URL.** Host sanitization now strips a trailing `:port` after the closing bracket of an IPv6 literal (so `[::1]:8765` no longer becomes `ws://[::1]:8765:8765`) while preserving the colons inside the brackets; the dedicated `port` field still wins.

## [0.1.4] - 2026-06-14

### Fixed

- **A malformed JSON control message no longer crashes the host.** A bad `advertise` / `unadvertise` / `advertiseServices` frame from a buggy or hostile bridge (for example a non-array `channels`) previously threw out of the WebSocket message handler, surfacing as an uncaughtException on Node and a fatal error on React Native release builds. The Foxglove dispatch now contains handler errors and routes them through the injected logger, and the affected handlers guard their field shapes so a half-valid frame degrades instead of throwing.
- **`FoxgloveClient.connect()` no longer hangs forever against a wrong or silent endpoint.** A socket that opened but never spoke the Foxglove protocol (the classic "rosbridge port in a Foxglove profile"), or that closed before the handshake completed, left the connect promise pending indefinitely. The connection timeout now covers the full handshake, and a pre-handshake close rejects the promise.
- **A failed initial `connect()` no longer leaves a background reconnect loop.** Both transports previously rejected the caller yet kept retrying in the background; because the manager only stores the client after a successful connect, that produced an unreachable client holding a socket nobody could disconnect. Auto-reconnect now runs only after a connection has previously succeeded, or while a reconnect cycle is already in progress; first-connect retry is the consumer's responsibility. `ProtocolManager.connect` also disconnects the client when `connect()` rejects.
- **Circuit-breaker cooldown timers no longer outlive the connection.** Connection teardown now destroys each subscription's breaker, so a tripped breaker's cooldown cannot fire into the next connection (where subscription ids are reused).
- **`RosbridgeClient` detaches its WebSocket handlers before closing**, so a late `onclose` from a stale socket cannot tear down a newer connection.
- **A pasted `wss://` or `https://` host no longer silently downgrades to plaintext.** When `secure` is unset the scheme is inferred from the host; an explicit `secure` (true or false) still wins.

### Changed

- **`base64ToUint8` no longer uses `atob`.** It decodes with a small lookup table instead, removing a global that is outside the library's supported set and absent on older React Native (Hermes) runtimes. Only the legacy JSON service-response path is affected; the decoded bytes are unchanged.

### Documented

- **Corrected the disconnect safety boundary.** The library publishes a zero-Twist stop on `/cmd_vel` only on an intentional disconnect while the socket is open. It cannot stop the robot on an unexpected loss of connectivity (network drop, app kill, crash) because the transport is already gone; network-loss halting requires a robot-side `cmd_vel` watchdog. Stated affirmatively in the README, both client class headers, and the `publishZeroTwist` TSDoc.
- **Documented post-reconnect behavior:** subscriptions are not re-established after an automatic reconnect, so the consumer watches `onStatusChange` and resubscribes.
- Added a SECURITY.md threat-model section: inbound size and count caps plus a fuzz harness are scheduled for a later hardening milestone, so connect only to bridges you trust until then. Removed a stale class-header line describing a keep-alive ping that was dropped in v0.1.1.
- Reordered the ROADMAP milestones (the read-only introspection surface before the Zenoh transport before the hardening milestone).

## [0.1.3] - 2026-06-02

### Added

- **`SubscribeOptions.dispatchMode`** controls how throttle-surviving messages reach the callback. `'immediate'` (the default, and the only prior behavior) parses and delivers every surviving message synchronously on the message-handler tick. `'latest-only'` delivers only the newest message under back-pressure: superseded messages are dropped *before* being parsed and delivery is deferred off the message-handler tick, so a high-bandwidth topic like a raw camera stream decodes only the frame you will actually render. The conflation happens upstream of the CDR/JSON decode, which an external wrapper cannot do because it only ever receives already-parsed messages. Available on both Foxglove WS and rosbridge. On a binary (CDR) topic the surviving payload is copied to outlive the deferral, so `'latest-only'` is parse-cheap but not allocation-free; on rosbridge the stashed frame is an immutable string and the stash is copy-free. It composes below the throttle (`maxFrequency` and the adaptive cap decide eligibility, then `'latest-only'` keeps the newest of those). A callback that throws is logged and never wedges the subscription; on unsubscribe, disconnect, or a circuit-breaker trip any pending message is dropped rather than delivered.
- **`materializeBytes(view: Uint8Array): Uint8Array`** returns an owned, offset-0 copy of a `Uint8Array`. `RosMessage.data`, when it is a `Uint8Array`, is a zero-copy view into the inbound WebSocket frame (v0.1.2); call this before retaining the bytes past the callback or handing them to a native binding that ignores `byteOffset` (some Skia paths, `node-canvas`, `sharp`, FFI). It always copies and never returns the input view, so the result is always safe to retain. This supersedes the v0.1.2 note that anticipated a conditional (skip-when-already-owned) copy: a full-span view can still alias the shared frame buffer, so the conditional form would have skipped the copy in exactly the unsafe case.
- **`matchesSchema(a: string, b: string): boolean`** compares two ROS schema names tolerant of the ROS 1 / ROS 2 `msg/` (and `srv/`, `action/`) asymmetry, so `sensor_msgs/msg/Image` matches `sensor_msgs/Image`. It is kind-agnostic: it strips the interface-kind segment and compares `pkg` + `Type`. A `normalizeSchema` counterpart is deliberately not exported, because a 2-part name cannot be safely expanded to canonical 3-part form (the interface kind cannot be inferred from the string).

### Changed

- **Bundled service-schema lookup now tolerates the 2-part / 3-part name asymmetry.** A bridge advertising a well-known system service as `rcl_interfaces/ListParameters` (without the `srv/` segment) now resolves to the bundled schema, so parameter operations and goal cancellation work regardless of which form the bridge reports. Bridge-advertised schemas remain authoritative.

## [0.1.2] - 2026-06-01

### Performance

- **Zero-copy payload view on Foxglove WS binary topic ingest.** Previously every inbound `messageData` frame allocated a fresh `ArrayBuffer` (`ArrayBuffer.prototype.slice`) for the payload, costing roughly 10 MB/frame on raw 1080p image streams even on frames that the throttle subsequently dropped before parse. The library now uses a zero-copy `Uint8Array` view; downstream consumers (CDR reader, JSON decoder, byte-size accounting) see no behavior change. Verified end-to-end against a sustained 138 MB/s harness: `max` lag dropped from 96 ms to 29 ms (3.4× tail reduction), `mean` and `p50` unchanged.

### Changed

- **Control-priority publishes now coalesce by destination.** When multiple `priority: 'control'` publishes for the same topic queue in the outbox during JS-thread saturation, only the latest drains rather than every queued tick in FIFO order. The release-the-joystick zero-Twist that follows N stale-value Twists on `/cmd_vel` now sends in one WebSocket frame, so the robot stops within one round-trip of release regardless of how deep the queue grew during the block. Insertion order across **distinct** topics is preserved (intra-topic conflation only). Reduced the worst-case stop latency by orders of magnitude under sustained-overload scenarios.
- **Tightened CircuitBreaker defaults for CDR-realistic workloads.** The breaker's `lagThresholdMs` (`250 → 150`), `tripDwellMs` (`5000 → 2000`), and the internal `WARMUP_MS` grace period (`2000 → 500`) were originally tuned against JSON-sim spike patterns (transient 100–333 ms spikes interleaved with healthy stretches). CDR sensor streams on real hardware fail in a different regime — sustained multi-second freezes during the cold-start window — which warrants faster detection. Total subscribe-to-unsubscribe floor on a genuinely saturating topic drops from approximately 7 s to approximately 2.5 s, comfortably below the threshold at which a user perceives the app as frozen.

### Documented

- **Zero-copy contract on `RosMessage.data` when it is a `Uint8Array`.** The byte values delivered to a subscriber callback as `Uint8Array` are now views into the inbound WebSocket frame's `ArrayBuffer`, not copies. The view's `byteOffset` is significant. Consumers handing `data` directly to native bindings that ignore `byteOffset` (some Skia binding paths, some FFI calls) must first materialize an owned copy via `new Uint8Array(data)`. A `materializeBytes(view)` helper that performs this copy conditionally is planned for the next release; until then the explicit copy is the recommended idiom. TSDoc on `RosMessage` carries the full contract.

## [0.1.1] - 2026-05-27

### Fixed

- **`FoxgloveClient.callService` against `foxglove_bridge >= 3.2.6` (foxglove-sdk-cpp v0.18.0+) hung until timeout because the bridge rejects JSON-encoded service requests** even when it advertises `supportedEncodings: ["cdr", "json"]` — that capability applies to topic messages, not service calls. Service-call requests are now CDR-encoded using the per-service `requestSchema` shipped by the bridge in `advertiseServices`; the response is decoded with the corresponding `responseSchema`. The fix is backward-compatible with older bridges (CDR is the canonical ROS 2 service encoding and has always been accepted). Verified at the wire level against ROS Jazzy + `foxglove_bridge` 3.2.6.
- **`FoxgloveClient` now handles the `serviceCallFailure` op** alongside `serviceCallResponse`. Failures from the bridge (unknown service, malformed request, schema mismatch, unsupported encoding) reject the in-flight call promise immediately with the bridge's message instead of being silently dropped until the 30 s timeout.
- **`FoxgloveClient.callService` against schemaless service advertisements now works for empty requests.** `foxglove_bridge` 3.2.6+ commonly advertises services with their type name but without inline request-schema text — the normal shape for services discovered via ROS 2 graph introspection rather than explicit `.srv` files. The client now detects this case: if the caller's request is empty (`{}`, `null`, or `undefined`), it sends only the 4-byte CDR encapsulation header and the bridge default-constructs the request server-side from the known type. Non-empty requests against schemaless services still surface a clear error explaining the limitation (the encoder genuinely cannot serialize without field-layout information).
- **`FoxgloveClient.callService` now resolves request and response schemas through a layered fallback.** Order of resolution: (1) the bridge-advertised `requestSchema` / `responseSchema` (authoritative when present), (2) a bundled IDL for six well-known ROS 2 system services — `rcl_interfaces/srv/{ListParameters,GetParameters,SetParameters,DescribeParameters,GetParameterTypes}` and `action_msgs/srv/CancelGoal` — which `foxglove_bridge` 3.2.6+ commonly discovers via introspection without shipping schemas inline, (3) the 4-byte encapsulation-header fallback for empty requests when neither source has a schema. Parameter operations and action cancellation now work against any compliant bridge configuration, not only ones that ship `.srv`-derived schemas. When defs are available, an empty caller request `{}` is now filled with zero values via `schemaToTemplate` rather than rejected on missing fields, making `{}` a stable "default request" sentinel across sim and real-bridge setups.
- **`FoxgloveClient` now dispatches inbound binary opcode `0x03` SERVICE_CALL_RESPONSE frames.** Previous revisions consumed only the JSON-op response shape; `foxglove-sdk-cpp` 0.18.0+ defaults to the binary 0x03 frame for every service-call response, so pending callIds never resolved and surfaced as 30-second timeouts. The binary path and the legacy JSON-op path now route through a shared decoder; both CDR and JSON response payloads are handled.
- **`FoxgloveClient` now sends SERVICE_CALL_REQUEST as the spec-defined binary opcode `0x02` frame** instead of the JSON op of the same name. The JSON form is not in the Foxglove WS v1 spec and is rejected by current bridges with a level-2 status message, leaving callIds hanging until the 30-second timeout.
- **`FoxgloveClient` no longer emits the JSON `ping` keep-alive every 5 seconds.** The op is not in the Foxglove WS v1 spec; modern bridges emit a level-2 status in response to each one. WebSocket-level RFC 6455 ping/pong handles connection liveness at the transport layer and does not need application-level emulation. Existing `pong` responses from older bridges are ignored without error.
- **`FoxgloveClient` now fast-fails in-flight service calls when the bridge sends a level-2 status message naming `serviceCallRequest`.** These undirected status messages do not carry a callId, so prior versions had no way to associate them with the failing call and all in-flight callIds hung until their 30-second timeout. The substring match keeps the rejection scoped to service-call surfaces; unrelated level-2 messages do not tear down healthy calls.
- **`FoxgloveClient` outbound binary frames are now sent as `Uint8Array`, not raw `ArrayBuffer`.** React Native's WebSocket native bridge silently drops `send(ArrayBuffer)` payloads above roughly 400 bytes; this manifested as 16-name `get_parameters` requests never leaving the device (confirmed via tcpdump). Sending via `Uint8Array` uses a different RN native serializer that handles every payload size we send. Same bytes on the wire for browsers and Node; this is load-bearing for React Native consumers and is covered by a regression test.

### Changed

- **`ProtocolClientOptions.onLatency` is no longer driven by `FoxgloveClient`** as a consequence of removing the JSON `ping`/`pong` keep-alive (see Fixed). The option remains in the public type and is still driven by `RosbridgeClient` via its dedicated latency-probe path. Foxglove WS RTT measurement will return when a portable spec-compliant signal is available; browsers do not expose `ws.ping()` from JavaScript.

## [0.1.0] - 2026-05-20

### Added

- Initial public release. `IProtocolClient` interface and two implementations: `FoxgloveClient` (Foxglove WebSocket v1, binary + JSON, CDR decoding) and `RosbridgeClient` (rosbridge v2 JSON over WebSocket, no `roslib` dependency).
- `ProtocolManager` factory with URL sanitization (strips `ws://`/`http://` prefixes, trailing `:port`, validates via `URL`).
- Per-subscription adaptive throttle driven by JS-thread lag (`SubscriptionBandwidth`), observable via `getSubscriptionStats`. The throttle curves themselves are overridable per-client via `ProtocolClientOptions.presetOverrides` — host applications shipping to a different device profile than the library's default tuning can supply their own bucket curves without forking. `BucketDef` and `ThrottleMode` are public types; `DEFAULT_PRESETS` is exported for consumers building extensions on top of the defaults.
- Per-subscription circuit breaker (`CircuitBreaker`) with exponential cooldown, manual retry, and disable. Observable via `getBreakerState`, `getBreakerNextRetryAt`, `onBreakerStateChange`.
- Control-priority publish outbox: `PublishOptions.priority: 'control'` for E-Stop, dead-man's-switch, and gesture-driven publishes that must not be starved by incoming-message parse work.
- `publishZeroTwist()` convenience for safety-critical disconnect / background paths.
- `ensureAdvertised(topic, schemaName)` to pre-advertise channels before time-critical first publish.
- Service discovery for both transports: `getAvailableServices`, `onServicesChange`.
- Schema templates: `getSchemaTemplate(schemaName)` derives default JSON from ros2idl, ros2msg, or JSON Schema declarations carried inline by Foxglove WS (returns `null` for rosbridge, which does not carry schemas inline).
- Diagnostics readers: `getMaxLagMs`, `getLagStats`, `getLagHistoryCsv`, `clearLagHistory` for consumers building "currently throttled" badges and bug-report exports.
- `DEFAULT_PORTS` constant: `{ 'foxglove-ws': 8765, rosbridge: 9090, zenoh: 7447 }`.
- Apache 2.0 license, security disclosure process, and contribution guidelines.

### Roadmap (not in this release)

- `ZenohClient` ships as an unimplemented skeleton (every method throws). `ProtocolManager.connect` throws a clear "Zenoh support is planned for v0.2.0" error for `protocol: 'zenoh'`. The class is not exported from `index.ts` in v0.1.0.
